# V100 memory lab

Fork roboczy `alexzhang13/rlm`, upstream `d04208afbad29ca675ab13478c40ee8bebc84bfe`.
Jedna kopia modelu w llama.cpp; SQLite FTS5, hierarchiczne streszczenia i osobny trening LoRA.
Profil startowy dotyczy V100 32 GB, CUDA 12.4, CPU bez AVX2 i istniejącego `~/ai-v100`.
To prototyp do pomiarów. Nie ma jeszcze wyników wydajności ani jakości na Twoim GPU.

## Instalacja

Rozpakuj projekt w `~/ai-v100/src/rlm-v100` i uruchom:

```bash
bash ~/ai-v100/src/rlm-v100/install-v100.sh
```

Instalator tworzy `venvs/memory-lab`, konfigurację `research/v100.toml` i wrapper `bin/v100-lab`.
Nie używa sudo. Nie zmienia działających venvów, sterownika ani oryginalnych wag.
Powtórne uruchomienie zachowuje konfigurację. Do instalacji potrzebny jest istniejący `env.sh`, uv i działający `venvs/train`.
`doctor` pokaże brak GGUF albo binarki. Nie pobiera i nie konwertuje wielkiego modelu w tle.

## Pierwszy pomiar

Terminal 1:

```bash
~/ai-v100/bin/v100-lab serve 2>&1 | tee ~/ai-v100/research/logs/server.log
```

Terminal 2, po komunikacie o gotowym serwerze:

```bash
~/ai-v100/bin/v100-lab bench
```

Wynik `research/logs/benchmark.json` zawiera ustawienia, odpowiedzi i medianę tok/s.
Każde wywołanie trafia do `research/logs/inference.jsonl`. Pomiar jest end-to-end,
bez streamingu; nie jest pomiarem czasu do pierwszego tokena ani benchmarkiem jakości.
`bench` jawnie wyłącza thinking w tym jednym teście szybkości. `bench --thinking`
mierzy wariant z thinking; wymaga wystarczającego limitu `max_output_tokens`.
Inne odpowiedzi zachowują domyślne ustawienia thinking serwera. Krótkie streszczenia
wyłączają thinking, żeby limit streszczenia nie został zużyty na samo rozumowanie.
Klient liczy tokeny z tymi samymi opcjami szablonu co generacja. Przy pustej odpowiedzi
loguje zużycie tokenów, finish_reason i liczbę znaków reasoning bez jego treści.
Serwer ma 1 slot, kontekst 8192, wszystkie warstwy na GPU, batch 512 / ubatch 128,
KV f16, flash-attention auto. Nie włącza mechanizmów przeznaczonych dla Ampere przez Tritona.
CPU nie musi obsługiwać AVX2: używana jest Twoja wcześniej zbudowana binarka llama.cpp.
Nie uruchamiaj serwera i treningu jednocześnie na tej karcie.

## Pamięć i źródła

```bash
~/ai-v100/bin/v100-lab ingest ~/dokument.txt
# Skopiuj wypisany identyfikator dokumentu:
~/ai-v100/bin/v100-lab summarize IDENTYFIKATOR
~/ai-v100/bin/v100-lab ask 'Co dokument mówi o pamięci?'
```

Obsługiwane są pliki tekstowe UTF-8. Import zachowuje cały oryginał, identyfikatory
i pozycje fragmentów. Tokeny liczy tokenizer faktycznego modelu przez llama.cpp.
Drzewo streszczeń ma fanout 4; ukończone węzły zapisuje od razu i ponowne wywołanie
kontynuuje od brakujących węzłów. Zmiana `runtime.model_version` unieważnia ich cache.
Zmień tę wersję po każdej zmianie wag/GGUF. Nie aktualizuj wag podczas aktywnej sesji.
Zmiana limitów pamięci również tworzy nową wersję streszczeń.

Wyszukiwanie jest leksykalne, nie semantyczne: inne sformułowanie pytania może ominąć
istotny fragment. Streszczenia ułatwiają znalezienie źródła, lecz odpowiedź dostaje
oryginalne fragmenty. W tej wersji rozwijanie drzewa może być kosztowne dla ogromnych
zbiorów. Nie jest to jeszcze zaawansowany agent RLM ani dowód poprawnego rozumowania.
Domyślny kontroler nie wykonuje kodu wygenerowanego przez model. Upstreamowe
`RLM(environment="local")` wykonuje Python na komputerze: venv go nie izoluje.

## Zmiana wag i checkpointy

`ask` zapisuje RUN. Umieść poprawną, sprawdzoną odpowiedź w pliku, potem:

```bash
~/ai-v100/bin/v100-lab feedback RUN_ID ~/poprawna-odpowiedz.txt
~/ai-v100/bin/v100-lab export ~/ai-v100/research/verified.jsonl
bash ~/ai-v100/src/rlm-v100/install-v100.sh --training
# Zatrzymaj serwer Ctrl+C, sprawdź nvidia-smi, następnie:
~/ai-v100/bin/v100-lab train ~/ai-v100/research/verified.jsonl
# Wznowienie po przerwaniu:
~/ai-v100/bin/v100-lab train ~/ai-v100/research/verified.jsonl --resume
```

Potrzebne są co najmniej dwie niezależne grupy źródeł. Pytania korzystające ze wspólnych
dokumentów trafiają do tego samego podziału, żeby nie przeciekać do ewaluacji.
Samo wygenerowanie odpowiedzi nie dodaje przykładu do treningu. Dotychczasowe zatwierdzone
przykłady pozostają w eksporcie jako replay. Nie jest to automatyczne uczenie z każdej rozmowy.

Trening: NF4 QLoRA, FP16 obliczenia, SDPA, rank 16, checkpointing gradientów,
assistant-only loss, maks. 1024 tokeny, mikro-batch 1, akumulacja 8. Możesz ustawić
`precision="fp16"` i zmierzyć szybkość, ale VRAM może być za mały przy tym samym kontekście.
Za długie przykłady są odrzucane z błędem, nie obcinane. Dopasuj źródła do limitu
treningowego; 8192 tokeny inferencji nie oznaczają automatycznie treningu na 8192.
Do konsolidacji sprawdzonej wiedzy w wagach możesz użyć `feedback RUN_ID plik.txt --question-only`:
trening dostanie oryginalne pytanie i zatwierdzoną odpowiedź, bez długich fragmentów źródeł.
Wtedy odpowiedź powinna być samodzielna, bez identyfikatorów cytowań. Pochodzenie źródeł
pozostaje w rekordzie. Ten tryb uczy wiedzy, a nie odpowiadania na podany dokument.

Logi w `research/checkpoints/skill-lora/metrics.jsonl`: train loss, eval loss,
gradient norm / LR gdy zwróci je Trainer, peak VRAM, liczniki tokenów i czas treningu.
Checkpoint co 25 kroków zawiera adapter, stan optymalizatora, schedulera, RNG i Trainer.
Znacznik `complete.json` powstaje po zapisie; resume wybiera ostatni ukończony checkpoint.
Manifest blokuje resume po zmianie danych, bazowego modelu lub parametrów. Dla nowego
zbioru ustaw nowy `training.output`. Zachowuj manifest i kopię środowiska.
Dla kolejnej rundy z nowymi danymi ustaw nowy `training.output` oraz `training.init_adapter`
na poprzedni katalog `candidate/`. Zachowaj oryginalny `training.base_model`.
Kontynuujesz wtedy naukę tych samych wag adaptera, z nowym stanem optymalizatora.
`--resume` służy do wznowienia przerwanej rundy z tym samym zbiorem i optymalizatorem.
Przy `init_adapter` używany jest rank zapisany w adapterze; zmiana pola `rank` go nie powiększa.

`candidate/` to adapter LoRA, nie pełne zmienione 12B ani GGUF. Wagi adaptera rzeczywiście
się uczą. Adapter można później scalić z oryginalnym modelem i wyeksportować nowy GGUF.
Nie jest automatycznie promowany: porównaj jakość na osobnym zbiorze, wiedzę ogólną,
polski, cytowania i regresje. Sam spadek loss nie dowodzi wzrostu jakości.
Po ocenie adaptera zatrzymaj serwer i uruchom `~/ai-v100/bin/v100-lab export-model`.
Polecenie używa osobnego `venvs/memory-lab-train`, lokalnej bazy FP16, zapisanego
adaptera i istniejącego `venvs/convert` oraz narzędzi llama.cpp. Tworzy `export-fp16/`,
`export-F16.gguf` i `export-Q6_K.gguf` w `training.output`. Potrzeba około 60 GB wolnego
dysku. Nie nadpisuje istniejących eksportów. Brak konwertera albo binarki kończy się
jasnym błędem; środowisko konwersji powinno mieć zależności wymagane przez przypięte llama.cpp.
Następnie zmień `server.model` na nowy Q6_K i `runtime.model_version` na nowy identyfikator,
zrestartuj serwer i porównaj benchmark oraz odpowiedzi. Automatycznej promocji nie ma.

## Dalsze optymalizacje

Najpierw baseline. Potem porównuj w `research/v100.toml`: ubatch 128/256, batch 512/1024,
flash attention auto/on/off oraz sloty 1/2. Dwa sloty zwiększają throughput przy
wielu zapytaniach, nie muszą przyspieszać jednej odpowiedzi i zużywają więcej KV.
Mierz tok/s oraz jakość przy tych samych promptach, temperaturze i wersji modelu.
GPU-util 100% nie jest celem samym w sobie.

Opcjonalny zgodny model draft GGUF: ustaw `server.draft_model` i `draft_tokens` 2/4/8,
restartuj serwer i powtórz pomiar. To draft-simple, nie MTP. Model draft musi być
zgodny z tokenizerem i wersją celu; nie ma automatycznego dobierania draftu. Akceptację
draftu i czasy natywne odczytuj z logów llama.cpp. Bez realnego przyspieszenia usuń draft.

Backend upstream:

```python
from rlm import RLM
from rlm.clients.llamacpp import LlamaCppClient
client = LlamaCppClient(context_window=8192)
# Local REPL wykonuje kod modelu. Używaj tylko w świadomie izolowanym środowisku.
rlm = RLM(backend="llamacpp", backend_kwargs={"context_window": 8192},
          context_window=8192, token_counter=client.count_messages,
          max_concurrent_subcalls=1, max_repl_output_chars=4096)
```

Opcjonalne SDK dostawców upstream instaluje się przez `pip install '.[providers]'`.
Ten fork nie zmienia architektury Gemmy i nie uruchamia abliteration.
